# GitLab 合并请求：产品与界面设计

状态：首版代码已接入 GitKit；界面与调度实现以第 14 节为准，远程实例验收尚未完成。

更新时间：2026-10-06。首版面向设置中所配置 GitLab 账号的所有可访问项目，支持 GitLab.com 与自建实例，不依赖当前打开或选中的本地仓库。

启用前提：设置中已保存 GitLab 账号凭据（非空 Token）与有效实例地址。未配置时不展示 MR 入口、提醒、列表与详情，也不注册 MR 数据订阅或发起远程轮询。账号设置入口保留在设置页。保存配置后自动启用；移除配置时立即收起界面并停止后续轮询，旧请求结果不得重新显示。已在执行的读取会在现有超时边界内结束，其结果丢弃。

## 1. 使用目标

用户目前在 GitLab 网站查看与合并 MR。GitKit 将这条日常流程接入应用级账号收件箱：

**状态栏发现相关 MR → 向上展开列表浮层 → 选中后收起浮层 → 在工作区阅读详情与远程差异 → 查看服务器合并条件 → 执行合并 → 在工作区确认结果。**

首版保留 GitKit 现有仓库与工具栏，以及底部状态栏。MR 详情使用整个白色工作区卡片，临时替换原分支侧栏与提交历史区域；返回工作区后恢复原历史界面。

## 2. “与我相关”的规则

汇总配置的 GitLab 账号在所有可访问项目中，处于 opened 状态且与我相关的 MR。未在 GitKit 打开或克隆的项目也包含在内；切换本地仓库不改变查询范围或列表。

满足以下任意条件即可进入列表，三项之间是 **OR**：

- author 是当前 GitLab 用户。
- assignees 包含当前 GitLab 用户。
- reviewers 包含当前 GitLab 用户。

身份来自所选 GitLab 账户的认证用户接口或 GraphQL currentUser。不能使用本地 Git 提交者姓名、邮箱或提交身份设置匹配。

同一 MR 只出现一次，但可同时显示“我发起”“指派给我”“我审核”多个关系标记。

账号与实例都参与隔离；同名用户名、不同实例、不同账号不能共享已读状态或结果。

## 3. 总数与“新”提示

- **相关 MR 总数**：满足上述规则的全部 opened MR，包含已看过和未看过的条目。
- **新 MR 数量**：其中尚未在 GitKit 查看过的条目；不是简单比较 created_at，也不是把所有 opened MR 都叫“新”。
- 旧 MR 新增我为指派人或审核人后，首次进入相关集合，也应能成为新条目。
- 从相关集合移除、关闭或合并后，不再计入状态栏数量。
- 推荐在成功加载某个 MR 详情摘要后标记已查看；仅打开列表不批量清除新提示。
- 详情查看过后出现新提交，首版用“有新提交”版本提示，避免把同一 MR 反复计为新 MR。

推荐首次成功连接时建立已有 MR 基线：显示相关总数，现有条目不全部触发“新”提示；此后新进入相关集合的条目才提醒。首次同步未完成或失败时不建立基线。

相关 MR 总数大于零时，底部状态栏左侧隐藏分支名与 origin 同步状态，只显示 MR 入口。有新条目时显示“n 条新合并请求”，全部已查看时显示“n 条合并请求”。总数为零时隐藏整个 MR 入口，恢复普通分支与 origin 同步状态。提醒入口悬停显示新条目数量、相关总数与最近成功检查时间。

Draft 仍属于相关 opened MR，在列表标记草稿并展示服务器限制，不假装可合并。

## 4. 列表与详情的交互

### 状态栏入口

- 相关 MR 总数大于零时，在底部状态栏左侧用 MR 入口替换分支名和 origin 同步状态；两者互斥，不能同时展示。
- 有未查看条目时显示“n 条新合并请求”，没有未查看条目但仍有开放请求时显示“n 条合并请求”。相关总数为零时恢复原状态栏，不保留空入口。
- 新条目使用克制的强调色和数量，不使用持续闪烁或反复弹出提醒。
- 已配置账号但没有相关 MR 时隐藏入口；未配置账号时隐藏整套 MR 功能并停止远程查询，通过设置页配置。
- 检查失败保留最近成功结果并标记未更新；不能把失败画成“没有 MR”。
- 点击立即在入口上方展开缓存列表，再按刷新规则校验，不等待网络后才显示浮层；再次点击入口收起。

### 锚定状态栏的 MR 列表浮层

列表采用非模态窄长浮层，约 380px 宽、560–620px 高，直接位于底部“n 条新合并请求”入口上方，从底部向上展开，左边沿与入口对齐。空间不足时限制在可见窗口内，背景工作区保持可操作。

浮层顶部呈现“所有项目”、当前 GitLab 用户、相关总数与新条目数量，提供手动刷新和最近检查时间。头部与关系筛选保持固定；数据多时仅中间列表区域使用实际可滚动容器，不滚动整个浮层。

紧凑列表行分多行展示：标题与新条目标记在上方，下一行标明完整项目路径；!iid、作者、来源 → 目标分支、角色标记、草稿/合并状态和更新时间分层排列。超长内容截断，标题可通过悬停或键盘聚焦查看完整内容。

提供“全部”“我审核”“指派给我”“我发起”关系筛选；“我审核”指 reviewers 包含我，不等于仍欠缺我的审批。筛选只改变当前视图，不改变相关总数的定义。

选择某条 MR 后收起列表浮层，将详情展示在整个白色工作区卡片内。

### 工作区详情页

- 整个白色工作区卡片临时替换原分支侧栏与提交历史区域，使用完整宽度展示 MR 详情；上层仓库与工具栏、底部状态栏保留。
- 无论当前处于仓库页、工作台还是未打开本地仓库，都可直接打开同一工作区详情；退出时恢复原界面。详情顶部有返回列表、项目路径、标题、!iid、角色、源/目标分支和在 GitLab 打开入口，右上提供“返回工作区”。
- 摘要显示作者、说明、服务器状态、流水线、审批与未解决讨论情况；不可读取的字段明确标记。
- 差异区域复用 GitKit 的文件列表与 Diff 阅读方式，内容来自该 MR 的远程差异版本。
- 底部呈现服务器允许的合并操作及相关选项，阻塞时显示具体原因。
- 返回列表重新展开原列表浮层，保持状态栏入口锚点，保留筛选、选择与滚动位置；再次进入详情保留合理的文件选择与阅读位置。
- “返回工作区”退出 MR 详情，恢复原分支侧栏与提交历史区域及之前的工作区状态。
- 自动刷新不重置滚动、选择和展开状态，不把正在阅读的代码换成新版本。

### 浮层收起与合并确认

点击浮层外部、按 Esc 或再次点击状态栏入口，均收起浮层。收起后保留筛选与列表位置；键盘关闭时焦点回到入口。执行合并时禁用重复提交，结果仍展示在当前工作区详情页。

合并确认在工作区详情页内展开，复用同一上下文。确认时清楚呈现目标、选项和审阅版本，操作结果在同一区域展示。

### 视觉方向与草稿边界

继承 GitKit 既有的中性灰背景、蓝色动作、紧凑列表行与现有圆角。采用状态栏提醒 → 入口上方窄长列表浮层 → 白色工作区卡片内详情 → 详情内合并确认的路径。

交互草稿使用演示数据验证提醒替换普通分支状态、浮层锚点与收起、列表实际滚动、进入工作区详情、返回列表与工作区、合并确认及结果状态。应用实现沿用此交互；草稿中的成功结果不表示实际合并，应用兼容性仍需实际 GitLab 实例验收。

## 5. 首版操作范围

当前包括：相关 MR 列表、关系标记、远程摘要与 Diff、服务器合并状态、立即合并，以及在项目允许时选择 Squash、删除源分支和编辑合并/压缩提交消息。作者可取消自己的开放请求（在 GitLab 中关闭，保留源分支），非作者审核人可批准当前查看的版本。

GitLab 的用户权限、受保护分支、合并方式和项目 Squash/源分支删除设置是最终约束。强制要求的选项展示为锁定，禁止的选项不能选择。

首版只提供立即合并。自动合并留待后续能力验证，届时必须区分“已设置自动合并”和“已经合并”。

批准前重新确认账号、审核人身份、源 SHA、目标分支、Diff refs 和版本 ID；GitLab 审批规则仍由写 API 判定。已经批准、版本变化或写结果不确定时禁止重复批准，需先刷新或重新审阅。勾选编辑提交消息时，通过 GitLab GraphQL 读取项目模板展开后的默认合并/压缩消息作为编辑初值；重新审阅新版本后刷新未编辑的初值，保留已编辑内容。只有修改过且非空的消息作为自定义值提交，未修改或留空时沿用 GitLab 默认模板。读取失败可重试，取消勾选后可继续使用服务器默认消息合并。

改动页支持单行评论：对代码行右键选择“评论”，在该行下方输入文本，底部仅提供“添加评论”和“取消”。新增行携带新行号，删除行携带旧行号，未改动行携带新旧行号；重命名文件同时保留变更前后路径。评论绑定当前差异版本及三项 SHA，提交前校验账号、MR 与最新版本。发送失败保留文本；结果无法确认时阻止在该输入框重发，并提供 GitLab 核实入口。成功后在该行与讨论页显示真实返回的讨论，并重新读取服务器合并条件。

当前不扩展成完整 GitLab 管理后台。评论编辑、回复、讨论解决、流水线操作仍通过 GitLab 页面处理。

## 6. 调度与缓存架构

### 应用级服务

由应用级 Rust 调度器统一维护账户身份、能力检测、列表摘要缓存、刷新时间、错误与进行中请求。前端订阅快照和上报可见状态，不自行建立轮询定时器。

全局状态栏呈现同一账户、同一实例中跨项目汇总的数据。切换仓库不重新配置账号服务，也不触发逐仓库查询；同一账号会话共享摘要与进行中请求。

账户缓存键包含账户标识与规范化实例地址，并校验凭据指纹与认证用户。详情、已读记录和操作以 GitLab 实例内全局 MR id 为键，服务从可信摘要解析项目 ID 与 iid 后调用对应项目 API；不能只用项目内 iid、分支名或本地路径。旧的项目级已读基线不会误用于账号总览，首次完整账号同步建立新的基线。

调度采用请求完成后安排下一次的单次定时器。同一键只有一轮刷新；并发入口复用进行中结果，不叠加轮询。

### 传输选择

首版使用全局 `GET /merge_requests` 的三组角色查询，每组带 `scope=all&state=opened`，分别使用 `author_id`、`assignee_id`、`reviewer_id`。列表的 `references.full` 提供完整项目路径；不为每个本地仓库轮询，也不为每行额外读取项目元数据。以下 GraphQL 方案保留为后续减少 HTTP 请求次数的优化方向，启用前需验证目标实例。

可在一次请求中使用三组 alias/connection 分别读取 author、assignee、reviewer 结果，再合并去重；不把减少 HTTP 次数说成服务器只执行一次查询。

若目标实例支持已确认稳定的 OR 过滤，可选用统一 connection。实现前检测实际 schema 与权限，不默认采用实验性的全局 Query.mergeRequests 或实验订阅。

GraphQL 字段/过滤器不兼容时，回退 REST 的三组角色列表查询。对实例缓存能力检测结果；业务权限失败不能被误判为“API 不支持”而无限切换传输。

摘要不包含完整 Diff、评论正文、所有 CI job、头像二进制或本地 Git 状态。详情与差异均按需读取。

### 完整性与分页

- 跟随 GraphQL pageInfo/cursor 或 REST 分页链接，不能静默只取第一页。
- 三组列表合并后计数，不能直接把三组数量相加。
- 缓存和单页大小有边界，但完整计数不能因此漏项；分页未完成时显示正在同步或统计不完整。
- 不完整或部分失败的轮次不能覆盖上次完整计数并宣称同步成功。
- 大账号的分页可分批读取并限制并发；完整计算过程中维持已知快照，完成后原子发布新集合。
- 完成分页代表完成一轮扫描，不代表所有页来自同一时刻。使用稳定排序和 MR 键去重；遇到列表变动、页边界重排或增量扫描时保留后续全量校准，不能宣称事务级完整计数。
- 若引入 updated_after 增量，必须保留周期全量校准；关闭、移除指派/审核关系、权限变化不能靠“增量追加”处理。
- 不假定 MR 端点支持 ETag/Last-Modified；只在具体实例和完整查询键上验证支持后使用。

### 账户切换与响应隔离

认证用户或凭据变更时增加 account epoch。请求捕获账户、epoch 与实例键；返回时只有仍匹配当前配置才可写入缓存。

退出账号后取消后续调度，清理该账号的内存授权上下文。迟到响应不得重新写回已经退出/切换的账号结果。

切换仓库不影响账号总览缓存；主动点击其他仓库或工作台时退出 MR 详情并进入所选界面。切换账号或实例后，UI 只能消费新账号 epoch 对应的快照，旧账号结果立即失效。

## 7. 刷新节奏

以下为讨论确定的产品默认值，不是 GitLab 的统一要求。

| 场景 | 间隔 |
| --- | --- |
| GitKit 前台，MR 列表浮层与工作区详情均未打开 | 60 秒 |
| 前台，MR 列表页可见 | 30 秒 |
| 前台，选中 MR 详情页可见 | 30 秒 |
| 前台，所选 MR 流水线运行中 | 15 秒，仅刷新该 MR 状态 |
| GitKit 后台、隐藏或最小化 | 5 分钟，覆盖所有快速模式 |
| 睡眠、断网或应用退出 | 暂停 |

后台优先级高于列表浮层、工作区详情与流水线状态。即使详情页留在打开状态，也不能在后台继续 15 秒轮询。

恢复前台、展开列表浮层和切换到已缓存账号时，检查最近成功缓存年龄：普通触发遵循 **15 秒成功缓存冷却**，可复用新鲜结果。

首次无缓存时可立即请求。冷却只基于成功完成时间；失败不能刷新缓存年龄并掩盖过期状态。

从系统睡眠恢复后先等待 **15 秒宽限期**，随后最多补一次所需刷新，多个 focus/网络恢复事件合并。期间用户主动操作可按操作优先级执行。

合并等写操作成功后，立即刷新自身 MR，绕过普通缓存冷却，并与其他入口合并；不因此刷新全部项目或所有 MR 详情。

发现新条目的最坏延迟约为当前间隔加网络与服务器处理时间。失焦、限流、失败退避或离线会延长延迟，不能承诺实时。

## 8. 错误与状态展示

- 网络错误或 5xx：保留缓存，有限指数退避并加入小幅随机偏移；建议上限 15 分钟，恢复成功后回到正常节奏。
- 429：优先遵守有效 Retry-After；缺失时使用退避。服务器要求的等待时长不能被客户端退避上限缩短。
- 401/认证失效：停止该账户自动轮询，显示重新认证入口与缓存已过期状态。
- 项目详情 403/404 或权限撤销：保留明确的详情错误，限制该详情的重试，不能停止其他项目的账号总览或把列表画成空。全局列表权限不足则按账号错误停止自动查询，待凭据修复。
- 部分字段无权限：只禁用相关详情/操作，能读取的列表仍可展示。
- GraphQL 项目或 connection 返回 null、REST 返回 404 时，核对项目映射、存在性与访问权限；GitLab 可能在无权或不存在时不返回 GraphQL errors，不能直接视为成功空列表或 API 不支持。
- 请求超时：下一次读请求可退避；写请求结果不确定时，先查询 MR 状态，不能自动盲重试合并。

UI 至少区分：初次加载、完整有效缓存、后台刷新、无相关 MR、统计不完整、过期缓存、认证失效、权限不足。

## 9. Diff 与合并的一致性

MR 差异使用服务器返回的 diff version 与 base/start/head refs，不使用“当前本地分支”和任意目标分支顶端替代 MR 比较范围。

差异缓存键包含账户/实例/项目/MR 和该 diff version 的 base/start/head refs。已审阅源 SHA 单独记录；源 SHA 相同也不代表 base 或差异版本必然相同。

自动摘要刷新发现新版本时显示“有新提交/差异已更新”，让用户更新阅读内容；已审阅版本不能被后台静默替换。

执行合并前重新读取最新服务器状态，确认权限、目标、配置与所选选项，并将用户已审阅的源 SHA 传入合并请求。

若源 SHA 改变，阻止合并并要求刷新审阅；409 明确展示版本已变。SHA 校验约束源提交，不宣称固定了目标分支或代替 GitLab 检查。

GitLab 是审批、CI、讨论、冲突及策略的最终判断方。本地合并预览不能覆盖服务器条件。

操作后分别展示已合并、已设置自动合并、失败、结果待确认。自动合并与服务器队列后续状态继续按节奏读取。

## 10. CPU、内存与安全边界

监控仅调用远程只读 API，不执行 git fetch，不更新远程跟踪引用，不改变 HEAD、暂存区、工作区或本地分支。

只有用户明确执行合并才调用写 API。远程合并成功后刷新远程 MR 状态，本地同步由用户现有流程决定。

摘要缓存使用有上限的账号集合；详情与 Diff 采用有容量和大小限制的缓存，离开详情后按策略回收。超大 Diff 明确展示限制，不一次性加载所有内容。

分页可流式建立完整 MR 键集合与计数，避免长期持有所有页面的完整响应对象。计数完整性与摘要保留容量分开处理。

远程内容未变化时不向 UI 发布重复数据更新；最近检查时间可独立轻量更新，不重建列表和 Diff。

轮询持久化快照不得包含 Token、Authorization、请求头或凭据。凭据继续使用账户服务，凭据存储迁移不夹带在轮询快照中。

## 11. 可测量的验收

- 验证三种角色的 OR、重复角色去重、多账号隔离与 provider 身份匹配。覆盖两个项目出现相同 !iid，确保列表、已读、详情、差异与合并目标独立。
- 用超过一页的数据验证完整计数；覆盖关闭、合并、指派/审核人移除和权限撤销。
- 验证冷却、前后台优先级、睡眠宽限、恢复合并事件、请求不重叠和账号迟到响应丢弃。
- 抓取请求数、响应字节、解析时间、缓存大小和 UI 更新次数；区分后台摘要与用户打开 Diff 的成本。
- 以相同仓库与数据集测量启用/关闭监控的空闲 CPU、唤醒次数、内存增量及长时间内存趋势，不预先承诺虚构百分比。
- 一页三组 REST 查询在前台 60 秒时约 180 次/小时；GraphQL alias 可减少 HTTP 次数，但分页、详情与能力检测会增加实际成本。
- 验证相关总数大于零时 MR 入口独占左侧，包含全部已读的情况；总数为零时隐藏入口并恢复普通分支与 origin 状态。切换仓库、进入工作台或没有本地仓库时仍可使用账号总览；列表浮层锚定入口并向上展开，点击外部/Esc/再次点击入口可收起，数据多时仅列表区实际滚动；选择 MR 收起浮层并打开整个工作区详情，返回列表保留筛选、选择与滚动，“返回工作区”恢复原历史；无变化时列表/Diff 不重复重建。
- 覆盖 429、断网、401、部分 GraphQL 错误、超大 Diff、写操作超时和 SHA 变化；结果不确定不能报成功。
- 使用实际 GitLab 实例完成读取与合并验收。静态构建和本地 mock 不证明远程权限、版本与服务器配置兼容。

## 13. 官方依据与方案区分

本文的角色规则、位置、锚定列表浮层与工作区详情交互、Rust 调度、缓存策略和轮询秒数是 GitKit 产品设计。以下链接用于核对平台事实，不代表这些能力已经在 GitKit 发布。

- [GitLab MR API](https://docs.gitlab.com/api/merge_requests/)：列表过滤、分页、详细合并状态、Diff refs、合并选项和源 SHA 校验。
- [GitLab GraphQL API](https://docs.gitlab.com/api/graphql/) 与 [资源参考](https://docs.gitlab.com/api/graphql/reference/)：查询、connection 分页及字段稳定性；以目标实例实际 schema 为准。
- [GitLab REST 分页](https://docs.gitlab.com/api/rest/#pagination)：分页链接及 per_page 边界。
- [GitLab 审批 API](https://docs.gitlab.com/api/merge_request_approvals/)：审批读取与版本/套餐能力。
- [GitLab Token scopes](https://docs.gitlab.com/security/tokens/access_token_scopes/)：read_api、api 与 Git HTTPS 仓库权限的区别。
- [GitLab 受保护分支](https://docs.gitlab.com/user/project/repository/branches/protected/) 与 [Auto-merge](https://docs.gitlab.com/user/project/merge_requests/auto_merge/)：服务器合并权限、检查与自动合并语义。
- [GitLab 限流](https://docs.gitlab.com/administration/settings/user_and_ip_rate_limits/)：429、Retry-After、自建实例限流与响应头边界。
- [GitLab ETag polling](https://docs.gitlab.com/development/polling/)：特定服务器路由的缓存机制，不能推导所有 MR 查询均支持条件请求。
- [GitLab Webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/)：可访问的接收端、配置权限与投递要求。
- [GitHub Desktop PR updater](https://github.com/desktop/desktop/blob/95d61e45257aa23eaa5003d0da5044ee1f72a777/app/src/lib/stores/helpers/pull-request-updater.ts) 与 [PR store](https://github.com/desktop/desktop/blob/95d61e45257aa23eaa5003d0da5044ee1f72a777/app/src/lib/stores/pull-request-store.ts)：当前选中仓库、焦点驱动、缓存、请求复用和增量读取的参考；不直接套用其周期或 GitHub 增量语义。

## 14. 首版实现边界

- 详情页顶部提供“下载差异”弹窗。先通过原生保存窗口下载 GitLab 原始 `.diff`；仅保存成功后切换为“获取 AI 提示词”，提供预览和复制。提示词固定下载对应的 MR 信息与完整 refs，不触发 AI 调用、批准或合并。下载前后核对 MR 全局 ID、当前差异版本、refs 和目标分支；取消、失败或版本变化不进入提示词步骤。原始响应上限 64 MiB，无法确认文件数量或明显受到服务端裁剪时拒绝导出；文本差异不包含二进制文件内容。真实实例兼容性与原生保存窗口仍需实际验收。
- 复用设置中的 GitLab 连接。仅需要配置实例地址与 Token；不要求本地仓库匹配。Rust 校验实例地址、禁止认证重定向，项目操作依据可信摘要里的项目 ID，网页入口校验同一实例与规范 MR 路径。
- 首版采用全局 REST 三角色列表查询。首次解析认证用户，后续同一凭据会话复用身份；跟随分页后按全局 MR id 合并去重。详情按需解析指定项目，不扫描所有本地仓库。GraphQL 能力检测与传输优化留待实际实例兼容性验证后增加。
- 汇总配置账号在所有可访问项目中的相关开放请求，切换本地仓库不改变账号服务。身份变更使旧请求失效；首次完整同步建立基线，后续新增相关条目才提醒。
- 状态栏提醒、入口上方窄长浮层、整个工作区内详情、固定版本远程 Diff、单行代码评论、讨论读取、Squash/删除源分支/编辑提交消息选项、立即合并、作者取消与审核人批准均接入原生命令。自动合并尚未接入。
- 本地服务最多保留 16 个账号上下文、每账号 5,000 条完整摘要、8 个详情与 4 个 Diff 版本，缓存和基线 ID 估算总预算为 64 MiB。活动完整摘要上限 16 MiB，单详情 40 MiB，Diff 子缓存 24 MiB；优先淘汰非活动账号与旧正文，切换账号释放非活动详情正文。单响应上限 16 MiB，分页集合累计 64 MiB、200 页。超过完整列表/响应上限会显示未完成同步并保留旧完整快照，不能以截断数据宣称完整计数。字节估算不等于进程 RSS，也不限制网络解析与 IPC 的瞬时副本；阈值后续依据真实项目测量调整。
- 前端只订阅快照并报告可见状态。定时器、前后台优先级、网络暂停、睡眠恢复宽限、请求合并、限流与退避由 Rust 负责。已查看记录单独持久化，不持久化凭据、MR 正文或 Diff。
- 合并前重新核对服务器条件、所确认目标分支、完整 base/start/head refs 与差异版本 ID；请求带源 SHA。GitLab 写 API 只支持源 SHA 校验，预检查不能原子锁定目标分支变化。结果不确定时展示核实入口，不自动重复发送写请求。本地 Git 分支与工作区保持现有同步流程。
- 本地 fixture 覆盖角色/分页/去重、错误与限流、固定差异、版本变化拦截、写请求结果待确认、调度/缓存与账号隔离。浏览器验证提醒、浮层、筛选、详情与重试、冻结版本、确认及结果流程。类型检查与构建验证接线。以上不代表目标 GitLab 的版本、套餐、Token 权限和项目策略已经验收，也不能替代真实空闲 CPU/内存测量。
